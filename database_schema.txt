📘 SD Finance – Relational Database Design & Architecture Notes

This document captures the final database design decisions, schema structure, and operational reasoning for the SD Finance application.
It is intended for future reference, maintenance, and safe evolution of the system.

⸻

🗄️ Database Choice

Database: PostgreSQL

Why PostgreSQL
	•	Strong ACID guarantees (financial data safety)
	•	Excellent relational integrity
	•	Handles concurrent users safely
	•	Industry standard for accounting & ERP systems
	•	Easy backup and restore

⸻

🏘️ Village Table

❌ Initial Design (Not Relational)

VID   - PK
VNAME - text
EMP   - list [emp1, emp2, emp3]

⚠️ Why This Is Incorrect
	•	Relational databases must not store lists in columns
	•	Breaks normalization
	•	Makes querying and integrity enforcement difficult

⸻

✅ Correct Relational Design

village
-------
vid (PK)
vname

Employees are linked via a foreign key in the EMP table, not stored as a list.

Why This Design Works
	•	One village → many employees
	•	Each employee belongs to one village
	•	Clean and efficient querying
	•	Enforced referential integrity

⸻

👤 EMP Table

emp
---
eid (PK)
ename
level ENUM('employee','accounts','admin','master','partner')
vid (FK → village.vid)

Notes
	•	Replaces the invalid EMP list design
	•	One village → many employees
	•	One employee → one village (current requirement)

✔ Clean
✔ Role-based access ready
✔ Fully relational

⸻

👥 Customer Table

The CID vs A.NO distinction is intentional and critical.

customer
--------
cid (PK)
ano              -- NOT globally unique
name
vid (FK → village)
eid (FK → emp)
pano             -- parent account number
aadhaar          -- nullable
fdt
tdt
amt
pamt
bamt
iamt
type ENUM('daily','weekly','monthly')
period
notes
created_at

Design Guarantees
	•	CID is the true system identity
	•	A.NO is employee-facing and may repeat across villages
	•	Parent account linking preserved via pano
	•	Missing or legacy data allowed using NULL

⸻

💰 Payment Table

Initial Thought

PID
CID
AMT
DATE
A.NO

⚠️ Redundancy Concern
	•	If CID exists, A.NO is technically derivable

However, employee workflow requires A.NO, so we intentionally keep it.

⸻

✅ Final Payment Table Design

payment
-------
pid (PK)
cid (FK → customer.cid)
ano                -- employee-facing identifier
vid (FK → village.vid)
amt
payment_date
created_at

Why This Is Correct (Intentional Denormalization)

Column	Purpose
CID	Internal, unambiguous system identity
A.NO	Number employees actually know and enter
VID	Disambiguates A.NO across villages
CID + VID	Guarantees correctness

This is not bad duplication —
it is intentional denormalization for usability, very common in accounting systems.

⸻

🔄 Data Entry Workflow (Employee Perspective)

Employees never see CID.

Employee Flow
	1.	Employee selects Village (UI-level selection)
	2.	Employee enters:
	•	A.NO
	•	Payment Date
	•	Amount
	3.	Backend logic:

SELECT cid
FROM customer
WHERE vid = :vid AND ano = :ano;

	4.	If found → payment inserted
	5.	If not found → error shown

Result

✔ Simple for employees
✔ Correct for the database
✔ CID remains internal

⸻

🔐 Integrity Guarantees

The following constraint is enforced:

UNIQUE (vid, ano) ON customer

What This Guarantees
	•	No duplicate customers within the same village
	•	Same A.NO allowed in different villages
	•	Safe and predictable payment mapping

⸻

👤 Users Table

users
-----
uid (PK)
username (UNIQUE)
password_hash
role ENUM('employee','accounts','admin','master','partner')
created_at

Notes
	•	Clean authentication design
	•	Ready for role-based access control (RBAC)
	•	Future multi-user support

⸻

🔐 Database Storage & Physical Security Strategy

Final Decision: Hybrid of Option B + Option C

🏆 Recommended Approach
	•	PostgreSQL runs on internal disk (fast, safe, reliable)
	•	External USB drive is used for:
	•	Encrypted backups
	•	Offline storage
	•	Emergency data protection
	•	Can be unplugged anytime (no corruption risk)

⸻

Backup (Fast & Safe)

pg_dump -Fc sd_finance > /media/secure_usb/sd_finance.dump

Restore Anywhere

pg_restore -d sd_finance sd_finance.dump

Why This Is Best
	•	No performance impact
	•	Zero corruption risk
	•	Same physical control over data
	•	Industry-standard financial practice

This is exactly how financial systems handle physical safety requirements.
